## 3. Classification, labels, and execution status

Classification is the plan's fixed planning property ([plan Section 7](mvp-implementation-plan.md#7-autonomous-implementation-safety-classification)). Execution status is the item's current operational state, and it changes as work merges. An AUTONOMOUS-READY item can still be WAITING-DEPENDENCY.

| Execution status | Meaning |
|---|---|
| READY | Not blocked, and every dependency is merged. It can be started now. |
| WAITING-DEPENDENCY | Not blocked, but at least one dependency is not merged yet. This is normal sequencing, not a blocker. |
| BLOCKED-HUMAN | HUMAN-DECISION-REQUIRED, and the unresolved decision prevents the item's acceptance criteria from being completed. |
| BLOCKED-EXTERNAL | EXTERNAL-DEPENDENCY, and the unselected provider prevents the item's acceptance criteria from being completed. |
| MERGED | The implementation pull request has merged and the GitHub issue is closed. |

The `blocked` label is applied only when the plan shows that the decision or dependency prevents the item's own acceptance criteria from being met. It is never used for ordinary dependency sequencing. A blocked item shows its BLOCKED status even while its dependencies are also unmerged.

Five non-autonomous items are **not** blocked, because the plan states that their decision or provider gates only a sub-scope outside their acceptance criteria: `MVP-008` (Administrator bootstrap), `MVP-030` (partial-performance compensation row), and `MVP-010`, `MVP-025`, `MVP-043` (acceptance met with a local or mock adapter). They keep their non-autonomous label, and their issues forbid implementing or defaulting the gated sub-scope. When their dependencies merge they become READY for their acceptance-criteria scope only.

At generation no work item had merged, so READY meant "no dependencies". After pull request #56, READY also includes items whose dependencies have since merged.

## 11. Maintaining this index

- GitHub issue state is live; the execution statuses above are a snapshot taken at generation. When an issue merges, closes, or has a blocker resolved, update its row and the affected queues in the same documentation change.
- Never renumber or reuse an `MVP-*` ID or an issue. A plan change that adds or removes a work item needs a new issue (or a closed issue with a reason) and a new row here.
- If a human resolves a decision or selects a provider, remove the `blocked` label from the issue, record the decision in the owning specification first (AGENTS.md Section 6), and update Sections 4, 6, and 7.
- Each issue's final Definition of Done line states merge authority for its classification under the governed merge policy ([`AGENTS.md`](../../AGENTS.md) Section 5.1). Keep that line in step with Section 5.1 and with the issue's classification label.
